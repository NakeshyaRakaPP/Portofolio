Case Study — 02 // Software Architecture & Dev

Proyek RELASKA — Sistem Akademik

Role System Analyst & Project Lead
Timeline 10 Weeks
Focus Academic Data System
Tools Draw.io, ERD/UML, MySQL
01 // PROBLEM

Student Records Scattered Across Spreadsheets

RELASKA managed grades, attendance, and class schedules across a mix of shared spreadsheets and paper forms. There was no single source of truth: teachers kept their own copies, admins reconciled discrepancies manually every semester, and there was no audit trail when a record was changed.

Before designing any interface, the project needed a formal project charter and scope definition — stakeholders disagreed on what "done" even looked like.

Document — Project Charter & Work Breakdown Structure (WBS)
02 // PROCESS

Modeling the Data Before the Screens

The process started with entity mapping: students, teachers, classes, grades, and attendance records were modeled as an ERD to define exactly how each piece of data related to the others. A UML use-case diagram followed, clarifying which actions each role — admin, teacher, student — was actually permitted to perform.

Only after the data model was validated with stakeholders did the interface wireframes begin, ensuring the UI reflected real relationships instead of guesswork.

ERD / UML — Academic Data Relationships
03 // SOLUTION

One Dashboard, Role-Based Access

The final system centralized grades, attendance, and schedules into a single dashboard with role-based views: teachers see and edit only their own classes, admins see the full academic picture, and students see a read-only summary of their own records.

Every change is logged, replacing the old manual reconciliation process with a built-in audit trail.

Mockup — Role-Based Academic Dashboard
04 // IMPLEMENTATION

From Data Model to Live Dashboard

The validated ERD was translated directly into a MySQL schema, and the UML use-cases became the access-control rules enforced on every route — so what admins, teachers, and students could see and edit in the interface always matched what the data model actually allowed.

Screenshot — Live Academic Dashboard
05 // RESULT

From Scattered Spreadsheets to One System of Record

Formalizing the project scope early and modeling the data before the interface meant the final build matched what stakeholders actually needed, with no late-stage rework of the data structure.

Insight: the biggest risk in a project like this isn't the interface, it's disagreement about what the data even means. Locking the ERD and use-cases first turned every later design decision into a straightforward translation, instead of a negotiation.
